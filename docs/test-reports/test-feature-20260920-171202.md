## Per-Feature Details

### Python wrapper (generated)
- **Role:** Python developer new to JuliaLibWrapping; follows commands literally.
- **Use Case:** Call `hello`, `escape_time`, `scale_inplace`, `mandelbrot` from the generated `jlw_example_py` package.
- **What they tried:** Wrote a minimal program using only the facade, installed numpy, ran with `PYTHONPATH=out`.
- **Discoverability:** Good. README + generated `_facade.py` docstrings give the signatures and surface/ownership rules.
- **Setup:** Worked as described (`python3 -m venv`, `pip install numpy`, `PYTHONPATH=out`).
- **Functionality:** All four calls succeeded. `mandelbrot(4, 3)` returned `dtype=int32`, `shape=(3, 4)` — i.e. `(height, width)` as the docs promise. `scale_inplace` mutated the caller's array in place (`[1,2,3] -> [2,4,6]`). `hello` returned `"Hello, world"`.
- **Expected vs Actual Outcome:** Matched.
- **Blocked steps:** None.
- **Friction points:** README only shows the `PYTHONPATH` route; the presence of `out/pyproject.toml` implies `pip install ./out` is also supported but it is never shown.
- **Doc suggestions:** Show `pip install ./out` (or explicitly say the non-bundle route is PYTHONPATH-only); add expected example output.

### C++ binding
- **Role:** C++ developer; treats the generated header as the ABI source of truth.
- **Use Case:** Call the library from C++ via `extern "C" { #include "jlw_example.h" }`.
- **What they tried:** Wrote a C++17 program reproducing all four calls, compiled with the documented command.
- **Discoverability:** Good — README explains the `extern "C"` requirement and the column-major layout.
- **Setup:** Compiled and ran cleanly (`c++ -std=c++17 -Iout ... -Wl,-rpath,...`).
- **Functionality:** `Hello, world`; `escape_time(0.75-ish coords)=33`; in-place scale produced `2 4 6`; 8×4 Mandelbrot grid printed correctly.
- **Expected vs Actual Outcome:** Matched.
- **Blocked steps:** None.
- **Friction points:** The C++ section never shows a `jlw_free` call; the reader must infer it from the "境界の規約" section or the repo example.
- **Doc suggestions:** Add one `jlw_free(r.value.data)` line to the C++ snippet.

### Fortran binding
- **Role:** Fortran developer; mirrors ABI structs with `iso_c_binding`.
- **Use Case:** Call the library from Fortran and read the column-major matrix directly.
- **What they tried:** Hand-wrote derived types + `bind(C)` interfaces, compiled with the documented command.
- **Discoverability:** Partial — README says to mirror the header but shows no literal derived-type code; the reader relies on the repo example `examples/fortran/demo.f90`.
- **Setup:** Toolchain worked (Homebrew gfortran 16.2.0).
- **Functionality:** The doer's exact program failed to compile for a **doer reason** (Fortran declarations after executable statements), not an API mismatch. After hoisting declarations (only change), it compiled and ran: `Hello, world`, `escape_time=33`, `scaled = 2 4 6`, and the 4×8 matrix read correctly as column-major. Struct-by-value C returns work with this gfortran.
- **Expected vs Actual Outcome:** Achieved against the corrected program.
- **Blocked steps:** None.
- **Friction points:** No minimum gfortran version / flags documented, and all four entry points return structs by value — a real ABI-compatibility risk that the docs don't mention.
- **Doc suggestions:** Add the literal `iso_c_binding` skeleton (or link the repo example inline from the Fortran section) and state a minimum gfortran version.

### Rust binding
- **Role:** Rust developer; uses `#[repr(C)]` structs and a `build.rs`.
- **Use Case:** Link the shared library directly by path (no `lib` prefix) and call all four functions.
- **What they tried:** Hand-wrote structs, an `extern "C"` block, `Cargo.toml`, and `build.rs`.
- **Discoverability:** Partial — README describes the build.rs *contract* ("pass the library path and an rpath, not `-l`") but shows neither `build.rs` nor `Cargo.toml`; the repo example covers it.
- **Setup:** cargo 1.98.1 worked.
- **Functionality:** The doer's exact program failed for a **doer reason** (`std::os::raw::c_int64` does not exist). After replacing `c_int64` with `i64` (only change), it compiled and ran: `Hello, world`; `escape_time=33`; `scaled: [2.0, 4.0, 6.0]`; 8×4 Mandelbrot grid correct.
- **Expected vs Actual Outcome:** Achieved against the corrected program.
- **Blocked steps:** None.
- **Friction points:** Platform library suffix, working directory, and rpath syntax are not stated; a reader must copy the repo's `build.rs`.
- **Doc suggestions:** Inline a minimal `build.rs` snippet in the Rust section.

### Julia-independent bundle
- **Role:** Python packager shipping to a machine without Julia.
- **Use Case:** `julia --project=. build_bundle.jl` → `pip install ./out-bundle` → `from jlw_example_py import hello` on a Julia-less host.
- **What they tried:** Built the bundle (35.5 MiB runtime closure), then installed into a fresh venv and ran the documented `python -c` snippet with `PATH=/usr/bin:/bin` and no Julia.
- **Discoverability:** Partial — install commands are shown, but *how* the bundled `libjulia` is located at runtime is never explained.
- **Setup:** `pip install ./out-bundle` succeeded, including the bundled runtime (`site-packages/jlw_example_py/bundle/lib/` with `libjulia`, `bundle/lib/julia/*`).
- **Functionality:** `hello("world")` printed `Hello, world` with no Julia on `PATH`. The Julia-independence claim holds.
- **Expected vs Actual Outcome:** Matched.
- **Blocked steps:** None.
- **Friction points:** README line 71 names `out-bundle/jlw_example_py/bundle/` but never shows the resulting `out-bundle/` tree (only `out/` is shown); `privatize` and the loader's `bundle/lib` search are undocumented. Also, `numpy>=1.20` is a pip dependency, so "pip install だけで動く" still needs index access.
- **Doc suggestions:** Show the `out-bundle/` tree, explain that the generated loader searches `bundle/lib` first, and that `privatize` rewrites the install name; note the numpy dependency.

## Issues Found

Ordered by severity (none blocking):

1. **Blind-surface artifact (high *perceived* but low *real* severity): many ABI conventions are only demonstrated in `examples/`, not in README prose.** `jlw_free` argument choice, borrowed-string length-only convention, `dims == (height,width)`, matrix orientation, `iso_c_binding` boilerplate, `build.rs`, and `Cargo.toml` are all shown by the in-repo examples. A reader who follows README alone (or an offline docs bundle without `examples/`) must infer them. This is only a problem if the examples are not shipped with the docs.
2. **`out-bundle/` layout is undocumented.** README shows the `out/` tree but not `out-bundle/`, and never states that the runtime lives under `jlw_example_py/bundle/lib` and is found by the generated loader's search order. (Medium)
3. **Runtime-linking mechanism (`privatize`, install-name rewriting) is never named.** README line 42 mentions `bundle = true` + `privatize` while lines 64–70 route users through `build_bundle.jl`/`standard_build`; it is never stated that `standard_build` privatizes automatically. (Medium)
4. **No golden/expected outputs anywhere.** No greeting text, no `escape_time` value, no matrix orientation check — downstream users cannot self-verify. (Low)
5. **Non-bundle Python install route is ambiguous.** Only `PYTHONPATH=out` is shown despite a generated `out/pyproject.toml`. (Low)
6. **Fortran ABI-compatibility risks unstated.** Structs are returned by value; no minimum gfortran version or flags. (Low)
7. **Bundle build flow omits `Pkg.instantiate`** (the manual non-bundle flow has it). Harmless here because `build-env/Manifest.toml` is tracked, but inconsistent. (Low)
8. **A declared `numpy>=1.20` dependency means the bundle is not fully offline-installable**, contradicting a literal reading of "pip install だけで動く". (Low)

Source-checked corrections to doer inferences (treating each "I think X lives in Y" as a candidate):
- `dims` order `(rows, cols) == (height, width)` — **confirmed** by `_lowlevel.py:176-186` (`shape=tuple(self.dims)[::-1]).T`) and by the observed `(3,4)` for `H=3,W=4`.
- `jlw_free` takes the `data` pointer, not the struct address — **confirmed** by `_lowlevel.py:120,203` (`cast(self.data, c_void_p)`).
- Borrowed strings use `length` only, no NUL terminator — **confirmed** by `_lowlevel.py:150-159` (`from_bytes` sets only `length`); C++/Rust produced correct greetings with non-NUL-terminated buffers.
- `JLWStatus.message` is NUL-padded — **confirmed** by `_lowlevel.py:255` (`rstrip(b"\x00")`).
- Bundle runtime discovery "completely undocumented / likely to fail" — **refuted**: the loader searches `bundle/lib` before the package dir (`_lowlevel.py:12-31`) and `privatize` makes `libjulia` self-locating.

### Misleading-doc findings and proposed signposts
1. **Misled:** Every doer concluded the C ABI matrix dim order/orientation was unstated. **Doc location:** README 91/102/123 say `(height,width)` and column-major, but the header gives only `int64_t dims[2]`. **Signpost:** state in "境界の規約" that `CMatrix_*.dims == (rows, cols)` and that element `(i,j)` is `data[i + j*rows]`; add a 2×3 worked example.
2. **Misled:** The bundle doer judged runtime `libjulia` resolution "the central gap, most likely to fail." **Doc location:** README line 60 ("loader looks next to the package") vs line 71 (runtime under `bundle/`). **Signpost:** one sentence: the generated loader searches `bundle/lib` first, and `privatize` rewrites the dylib install name to `@loader_path`, so no env vars are needed.
3. **Misled:** Doers could not verify any output because no golden values exist. **Doc location:** README per-language sections. **Signpost:** add expected output blocks (e.g. `Hello, Python`; `escape_time(0.5,0.5)`; `mandelbrot` shape) beside each command.
4. **Pure rejects (doer errors a clear doc would not have provoked; do not re-raise):**
   - Fortran: declarations after executable statements — basic Fortran, not a doc issue.
   - Rust: `std::os::raw::c_int64` — nonexistent type, not a doc issue.

## Suggestions

Ordered by impact:

1. Add a short "ABI at a glance" block to README: `dims == (rows,cols) == (height,width)`, element address `data[i + j*rows]`, borrowed vs owned, and one `jlw_free(value.data)` example per compiled language.
2. Show the `out-bundle/` tree and explain the loader search order + `privatize`/install-name rewriting.
3. Add expected-output snippets next to each language command so users can self-verify.
4. State the non-bundle Python install options explicitly (`PYTHONPATH=out` vs `pip install ./out`).
5. State a minimum gfortran (and note struct-by-value returns) and pin a Rust edition.
6. Note the `numpy` dependency when describing the "no Julia needed" bundle.
7. Prefer backing each doc snippet with a compile-checked example file (the repo already has `examples/**`; `run_all.sh` keeps them honest) so prose and code cannot rot apart.
